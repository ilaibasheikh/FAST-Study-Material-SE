Q1.
a)Entities 
7 entities(tables): 
BOOK, BOOK_AUTHORS, PUBLISHER, BOOK_COIPES, BOOK_LOANS, LIBRARY_BRANCH, BORROWER

b) Primary keys:
BOOK: BookId
BOOK_AUTHORS: AuthorName
PUBLISHER: Name
LIBRARY_BRANCH: BranchId
BORROWER: CardNo

c) Foreign keys:
BOOK: PublisherName, references PUBLISHER(Name) to link publishers to books
BOOK_AUTHORS: BookId, references BOOK(BookId) to link book authors to books
BOOK_COPIES: BookId, references BOOK(BookId) to link book copies to books
	+ BranchId, references LIBRARY_BRANCH(BranchId) to link book copies to library
BOOK_LOANS: BookId, references BOOK(BookId) to link book loans to books
	+ BranchId, references LIBRARY_BRANCH(BranchId) to link book loans to library
	+ CardNo, references BORROWER(CardNo) to link book loans to borrowers

d) Domain:
BOOK:- BookId: NUMBER PRIMARY KEY, Title: VARCHAR(50), PublisherName: VARCHAR(50) FOREIGN KEY
BOOK_AUTHORS:-  BookId: NUMBER FOREIGN KEY, AuthorName: VARCHAR(50) PRIMARY KEY
PUBLISHER:- Name: VARCHAR(50) PRIMARY KEY, Address: VARCHAR(100), Phone: NUMBER(11)
BOOK_COPIES: BookId: NUMBER FOREIGN KEY, BranchId: NUMBER FOREIGN KEY, No_Of_Copies: NUMBER
BOOK_LOANS: BookId: NUMBER FOREIGN KEY, BranchId: NUMBER FOREIGN KEY, CardNo NUMBER FOREIGN KEY, DateOut DATE, DueDate DATE
LIBRARY_BRANCH: BranchId NUMBER PRIMARY KEY, BranchName: VARCHAR(50), Address: VARCHAR(100)
BORROWER: CardNo NUMBER PRIMARY KEY, Name: VARCHAR(50), Address: VARCHAR(100), Phone: NUMBER(11)

e)There is a One-to-many relationship between BOOK and BOOK_AUTHORS. BOOK is referencing BOOK_AUTHORS with BookId foreign key. One author who has written multiple books, the AuthorName will be repeated in BOOK since author is the same hence one.

1)
a) Referential integrity constraint will make the related tables consistent.It guarantees that a foreign key in one table must match a primary key in another table or be null.

b)
Foreign key can be null when database is designed to allow optional relationships between tables.
Eg 1: In a company, employees may be assigned to project or not. So in this case, project_id foreign key in employees table can be null for employees not assigned to any project

+------------+        +--------------+
| Projects   |        | Employees    |
+------------+        +--------------+
| project_id | <----- | project_id   |
|            |        |              |
|            |        |              |
+------------+        |              |
                      +--------------+


Eg 2: In a school, students may be enrolled in a course or not. So, the course_id foreign key in the Students table can be NULL for students not currently enrolled in any course.

+------------+        +------------+
| Courses    |        | Students   |
+------------+        +------------+
| course_id  | <----- | course_id  |

                      +------------+

c)When the record in the first table ( primary key) is updated/deleted, these actions can occur:
CASCADE: automatically updates/deletes the foreign key in the second table.
SET NULL: automatically sets the foreign key in the second table to NULL.
SET DEFAULT: automatically sets the foreign key in the child table to its default value.
NO ACTION: enforces the constraint and does nothing if the constraint is violated.
RESTRICT: prevents the updating/deletion of a record in the first table if it is referenced by any records in the second table.

2)
Inherent Model-Based Constraints: enforced by the DBMS itself, ensuring data integrity rules like primary keys(no duplicate entries) and foreign keys(maintains data consistency).
Schema-Based Constraints: constraints are defined within the database schema, such as CHECK(data meets condition), UNIQUE (vlaues aredifferent), and DEFAULT(default value for a column) constraints, NOT NULL Constraints(no empty values).
Application-Based Constraints: implemented through application logic, access rights(only admin can retrieve certain data) enforcing business rules and validation beyond what is covered by schema constraints.

A superkey is any set of attributes that can uniquely identify a row in a table, but it may contain extra attributes. 
Eg: Superkey: (emp_id, emp_name) It can uniquely identify rows but includes unnecessary email.
Key: (emp_id) It can uniquely identifies rows).
Every key is a superkey, but not all superkeys are keys.
